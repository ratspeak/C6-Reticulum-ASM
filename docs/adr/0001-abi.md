# ADR-0001: RISC-V psABI (ILP32) calling convention

- **Status:** Accepted
- **Date:** 2026-05-01

## Context

This project is pure assembly. There is no compiler enforcing a calling convention on us. We
must therefore choose one and apply it consistently across every function in the codebase, or
we will pay for the lack of discipline in interoperability, debuggability, and integration
of vendored asm references.

The candidates are:

1. The standard RISC-V psABI (ILP32 for our 32-bit target). This is the convention every
   RISC-V toolchain, debugger, and operating system assumes. It is documented, ratified, and
   used by every vendored crypto reference we will draw on (HACL\* outputs, fiat-crypto,
   BearSSL, Vale-extracted asm).
2. A project-internal convention optimized for our specific code patterns. This could yield
   marginal performance wins (e.g., different register saving conventions for hot crypto loops)
   at the cost of breaking everything external.

## Decision

Every function in this repository follows the standard RISC-V psABI (ILP32) calling convention,
strictly. Specifically:

- **Argument registers:** `a0`–`a7` (`x10`–`x17`) for integer arguments, in order.
- **Return registers:** `a0` for primary return, `a1` for secondary return (e.g., a length
  alongside a pointer). Wider returns spill to memory pointed to by an implicit first argument.
- **Caller-saved (clobberable):** `t0`–`t6` (`x5`–`x7`, `x28`–`x31`), `a0`–`a7`, `ra`.
- **Callee-saved (must preserve):** `s0`–`s11` (`x8`, `x9`, `x18`–`x27`), `sp`, `gp`, `tp`.
- **Stack pointer:** `sp` (`x2`), 16-byte aligned at function entry.
- **Return address:** `ra` (`x1`), saved on stack by non-leaf callees.
- **Frame pointer:** `s0` (`x8`) when used; not required for leaves.
- **Global pointer:** `gp` (`x3`), set by the runtime at boot, not modified by functions.
- **Thread pointer:** `tp` (`x4`), unused on a no-OS single-core target; treated as reserved.

The `@inputs`, `@outputs`, `@clobbers`, and `@preserves` fields in every function's spec block
describe its register usage in psABI terms. Static analysis can verify these against the asm.

## Consequences

### Positive

- Every general-purpose RISC-V debugger (`gdb`, `lldb`, qemu's monitor, Sail simulator output)
  produces correct stack traces and register dumps without per-function annotation.
- Vendored crypto references can be dropped in with at most a renaming pass; we do not have
  to rewrite their register usage.
- Future work that wants to drop in a small piece of compiled code (a vendor blob, a Sail-
  generated reference) is mechanically possible. We are not committing to ever doing this, but
  we are not boxing ourselves out of it.
- Symbolic execution tools (angr, KLEE) and verification tools (SAW) understand the convention
  natively. We do not have to teach them about a custom one.

### Negative

- We pay any psABI inefficiencies (e.g., callee-save spills that could have been avoided in a
  tight loop). In practice the impact is small on RV32IMAC and the verification savings dominate.
- A strict reading forbids cute optimizations like "return through `t0` because it's already
  there." The discipline is the point.

### Neutral

- The psABI does not specify floating-point conventions for our target (RV32IMAC has no F or
  D extension), so no decision is needed there.
- Atomic operations (the A extension) follow the standard RISC-V memory model.

## Alternatives considered

**Custom convention.** Reject. The only argument for it is marginal performance in hot loops,
which we can recover by inlining or using leaf-function discipline within the standard ABI.
The cost — every external tool needing project-specific awareness — is unjustifiable across
a multi-year project with formal verification.

**Hybrid (standard at module boundaries, custom internally).** Reject. The boundary becomes a
constant source of bugs and the verification story becomes per-module rather than uniform.
